# 待定决策与待焊清单

> 本文件配合 [设计规范 v2](设计规范-v2.md) 使用。规范主干已可动工，但有三处致命矛盾必须先焊。下面分两部分：**需要源（你）拍板的策略决策**，和**一致性审查发现、需在实现前/中焊接的清单**。

---

## 一、待定策略决策（需用户拍板，均附推荐默认）

1. 模态默认翻转(可见区优先OCR、视口外才升structured)是否锁死为不可覆盖,还是允许调用方显式声明 prefer_structured 强行直读DOM全树(代价:每次触发深度读取授权+高ε倍率)。推荐:锁死默认方向,但允许 prefer_structured 作为带授权代价的显式逃生舱。

2. ε_pool 的具体加权倍率需用户定量标定:structured-offscreen、background_silent 各自相对 pixels-可见区(1×基准)的倍率,以及二者叠加是否真用乘法(可能爆预算到不可用)。推荐:offscreen 3×、background_silent 4×、叠加取 max 而非乘积以避免预算瞬间归零,待用户确认。

3. narrated 子代理输出硬上限 N tokens 与 analyzed 结构化结果硬上限 M tokens 需用户给具体数值(影响截断 truncated=true 的触发频率)。推荐:N=512、M=2048 起步,后续按实际调。

4. 异常库的初始进程名/标题正则清单(password manager / banking / auth / wallet 类)需用户提供本机实际清单或确认用一份通用默认清单。推荐:先用通用关键词清单(1password/bitwarden/keepass/lastpass、bank、wallet、authenticator 等)+ 用户可增删。

5. 云子代理用于 narrated 时'只能收到已脱敏图'——脱敏后的图若仍含未被规则覆盖的敏感视觉信息(如手写、二维码、非PII敏感图表),是否需要额外人级确认才允许外送。推荐:允许外送但回执 what_left 必须逐项申报,且对二维码/条形码增加专门检测器后续迭代。

6. bring_to_front 这一'不可收束副作用'是否默认完全禁用(只在用户显式选 occlusion=bring_to_front 时启用),还是允许 auto 后端在其它遮挡策略全失时自动回退到它。推荐:默认禁用自动回退,必须调用方显式选择,因为它会产生用户可见的画面闪现且无法原子撤回。

7. CDP 后端(--remote-debugging-port)是否要在文档中标为'高级用户可选增强路径'并给出启用指引,还是完全不依赖它(本机默认不存在)。推荐:核心管线完全不依赖CDP,仅作为'若端点存在则解锁离屏截图/跨标签DOM不夺焦'的可选增强,文档附录说明。

## 二、一致性审查待焊清单

### 致命（3 条）

**致命.1** ε_pool 扣费点自相矛盾,且与并发合并/去重三处规则打架。§7.1 明文锁死'读像素即消费,不论最终是否入上下文',扣减点在 ANALYZING/NARRATING(EXIT_GATE 内)入口;但 §5.3 又把计量单位定义为'泄露面加权信息量'(structured 按提取字符/节点数折算)。问题:structured 路径根本不'读像素',它在 CAPTURING 阶段就已经把 DOM/UIA 全文拉进了进程内存——此时扣费点(EXIT_GATE 内)远在实际信息获取之后,中间经过 VALIDITY/SECURITY 两道闸门,若在闸门被 block/collapse,structured 的信息其实已经被'读'过(在子代理判官转述时甚至已外送),但按 §7.1 还没到扣费点=不扣 ε。这给出一条'反复触发 structured 捕获→在 EXIT_GATE 前被 block→不扣预算'的免费拼接通道,正好是 ε_pool 要堵的攻击。§10 去重又规定'重复帧不入 sink 但真实快门仍按加权计 ε',与'扣费点在 EXIT_GATE 内'直接冲突(去重发生在 SAMPLING/sink 之前)。三处对'何时扣、扣什么'的定义不一致。

- **修法**：把扣费拆成两段并统一锚到'信息离开源进程那一刻'而非'入上下文那一刻':(1) 预扣 reserve 在 AUTHORIZING(admission control,已有);(2) 实扣 commit 锚定到'modality 实际物化数据'的那一步——pixels=后端返回帧(CAPTURING 出口)、structured=DOM/UIA 拉取完成(CAPTURING 出口)、ocr=OCR 完成——而不是 EXIT_GATE。EXIT_GATE 之后的 block/collapse 只作废'入上下文',不退已 commit 的 ε(因为信息已被进程读取,拼接风险已发生)。去重的'真实快门计费'与并发合并的'shared_capture 共享一次计费'据此自动自洽。删掉 §7.1 里'读像素即消费,不论是否入上下文'这句对 structured 不成立的措辞,改为'物化即消费'。

**致命.2** '永不静默失败'承诺仍有一条结构性缝隙:授权件验签/异常库匹配本身失败时无回执出口。§7.2 转移表只覆盖了 AUTHORIZING 进入之后的失败(预算不足、捕获错误等),但 §5.1 入口闸门的前置步骤——八字段验签失败、在窗判定失败、异常库'只读窗口标题/进程'这一步本身抛错(如进程已退出导致 OpenProcess 失败、标题读取 race)——没有对应的 FAILED(verdict) 状态和固定回执。更尖锐:§5.2.1 后台静默命中异常库时'连授权问询都不发,fail-closed',但'fail-closed'在这里是否产出固定回执信封?如果只是静默拒绝不回执,就直接违反了立身铁律'永不静默失败'。状态机 IDLE→AUTHORIZING 这条边的失败语义是规范的盲区。

- **修法**：在 §7.1 状态枚举补 PREFLIGHT 子态(IDLE→PREFLIGHT→AUTHORIZING),并在 §7.2 加三行转移:PREFLIGHT 验签/在窗失败→FAILED(unauthorized_token);PREFLIGHT 异常库探针自身抛错→FAILED(preflight_probe_error,fail-closed);PREFLIGHT 异常库命中→FAILED(blocked_by_exception_lib,appealable=false)。明确所有这些 FAILED 都产出完整回执信封(content=null,completeness.validity_verdict 说明失败种类),包括后台静默命中异常库那条——它 fail-closed 但仍回执,只是回执不含被拒窗口的任何像素/标题细节(只说'命中受保护类别')。

**致命.3** §2.1 模态默认翻转('可见区优先 OCR,视口外才升 structured')与 §3.2 决策表的 dom 行默认模态(structured)直接冲突,且与函级预设 read.ocr/shot.element 的语义不闭合。当调用方走 element{by:dom(...)} 时,§3.2 决策表第一行写死'默认模态=structured';但 §2.1 和 §12 默认表写死'文本目标默认走可见区 OCR,仅视口外才 structured'。同一个'读 Chrome 里某文本元素'的意图,两节给出相反的默认后端。更糟:OCR 可见区需要先 pixels 截图再 OCR,而 dom 寻址的前提恰恰是'用 CDP/JS 直接拿 DOM 不截图'——两条默认路径用的是完全不同的句柄(os_window/mcp pixels vs chrome_tab JS),无法在解析后再切换,必须在寻址期就分流。

- **修法**：统一为:模态默认翻转只对'语义意图未指定寻址机制'(代级 ELICIT 或 target=app/window 文本意图)生效——此时默认 OCR 可见区。一旦调用方显式用 element{by:dom} 寻址,即视为已选择 structured 路径(§12 的 prefer_structured 逃生舱被隐式触发),自动挂深度读取授权 + 高 ε 倍率,不再被 §2.1 默认覆盖。在 §3.2 决策表 dom 行和 §2.1 都加一句交叉引用,说明'by:dom 即等价 prefer_structured,自带授权代价';并在 §2.7 约束矩阵加一行:'by:dom × 无 extract_structure 授权 → 解析期 fail-closed,提示需深度读取授权或改用 OCR 可见区'。

### 重要（5 条）

**重要.1** strict validity 在无 script 判据时'自动降 narrator'(§8 铁律)与隐私/外送规则冲突,可被用作绕过 allow_egress 的侧信道。§8 规定 strict 无判据→自动升 narrator(子代理读图转述);§11.5 规定 narrated 子代理若为云模型=外送像素须 allow_egress。组合后果:调用方只要请求 validity=strict 且选一个'无 script 判据'的 modality/场景,就能让系统'自动'把图喂给云子代理——这是一次未经 allow_egress 显式授权的自动外送。'自动降级'与'外送须每次单独授权'两条铁律在此打架:自动降级不可能停下来要 allow_egress,否则就不是'自动'。

- **修法**：给自动降级加授权护栏:strict 无 script 判据时,先检查 narrator 判官是否为本机模型。本机判官→自动降 narrator(无外送);判官为云模型→不自动外送,而是降级为 FAILED(unverifiable_needs_egress_auth) 或在已持有 allow_egress 时才自动走云 narrator。在 §8 铁律和 §11.5 各加一句把这条联动写死,消除'自动降级可静默外送'的缝。

**重要.2** bring_to_front 的'不可收束副作用'与收束铁律、与候选策略 all 在多实例下的组合,产生未定义且用户可见的连环夺焦。§3.3 说 bring_to_front 仅在 foreground 且 sink≠background 时允许,回执申报 irreversible_side_effects。但 §3.2/§3.3 未定义:当 candidate_policy=all 且 occlusion_policy=bring_to_front,对 N 个被遮挡实例会发生什么?按字面=逐个提到前台再截,产生 N 次画面闪现且每次夺焦改变前一次的'前台'判定(把刚截的盖住),candidate_resolution 和 focus_state 无法稳定申报。此外收束发生时(授权降级),已 brought_to_front 的窗口不会被放回原 z-order(诚实边界已承认),但'同链排队的后续 bring_to_front'是否取消?§5.4 收束只说'取消同链排队截图',没说取消排队的物理夺焦动作。

- **修法**：在 §2.7 / §3.2 非法组合补一行:candidate_policy=all × occlusion_policy=bring_to_front → 解析期 fail-closed(多实例逐个夺焦的 z-order 抖动不可申报),要求调用方改用 offscreen_render 或把 all 收窄为 frontmost。在 §5.4 收束原语明确:收束取消的'同链排队'包含尚未执行的 bring_to_front 物理动作(只是已执行的无法回滚),回执 collapsed 申报'已取消 K 个待执行夺焦'。

**重要.3** §7.5 类(b)语义谓词'移到 EXIT_GATE 的 result_only 档求值',但这与 §7.3 轴 A(重捕获针对'类 a 谓词不满足')和'期望谓词破解死锁'的初衷部分落空。死锁原本是:校验内容正确性需读语义,但预检禁读语义。方案把语义校验后移到 EXIT_GATE。但 EXIT_GATE 已是放行链末端——若此处 contains 正则不满足(拿到了渲染完整但内容错/旧的页面),状态机给的是 FAILED(expectation_violated),而无法回到轴 A 重捕获(重捕获循环在 VALIDITY_PRECHECK 阶段,早已走过)。结果:'渲染了但是错的/旧的'这个 §设计明确想抓的场景,被抓到了却只能失败,不能像 liveness 那样重试。这与 watch/on_change 的语义(等到内容对了为止)不闭合——on_appear(pred) 的 pred 是语义谓词时尤其断裂。

- **修法**：为'语义谓词 + 触发型 when(on_appear/on_change)'开一条从 EXIT_GATE 回 ARMED/CAPTURING 的受控重试边,但带独立预算(每次语义校验=一次受控消费,计 ε),max 次数复用 max_reattempts,耗尽→FAILED(semantic_expectation_unmet)。或在 §7.5 明确声明:语义谓词只支持'一次性校验'(satisfied/violated),不支持'轮询直到满足';若调用方要'等到内容对',必须用 when=on_change + 类(a)代理谓词触发、再在 EXIT_GATE 做类(b)终检。把这个限制写进规范而不是留空。

**重要.4** §11.5 'narrated 子代理只能收到已脱敏图,不得收原图',但脱敏器(§6)是'结构内容脱敏器',对 pixels 模态只有像素打码(allowlist 级),而 narrated 的输入恰恰是 pixels 原图。问题:像素打码只对'未授权应用'打码,对已授权应用窗口里的密码框/信用卡号视觉内容不打码(像素层不知道哪个矩形是密码框——那是 §6.1 节点类型剥离的能力,只在 structured/OCR 路径有)。于是'已脱敏图'对一张授权应用的截图=几乎等于原图(只有未授权应用矩形被盖)。承诺'子代理只收脱敏图'在 pixels 路径上名不副实:授权应用内的敏感视觉照样外送。这是 open_decisions 第5条点到的'脱敏后仍含未覆盖敏感信息',但规范正文把它当已解决铁律写,过度承诺。

- **修法**：诚实降级该承诺:在 §11.5 明确'已脱敏图'在 pixels 路径仅指'未授权应用已打码 + 可选 redact.pixel rects + auto_ocr_pii 命中区掩码',并显式声明'授权应用窗口内的敏感视觉内容不被自动脱敏,外送前须回执 what_left 逐项申报并(按 open_decision 5)对二维码/PII 视觉增检'。把它从'铁律'语气改为'尽力+申报',与 §1 立身定义'永远知道缺了什么'一致——这里缺的是'像素脱敏覆盖不到语义敏感区',必须申报而非假装覆盖。

**重要.5** PrintWindow(PW_RENDERFULLCONTENT) 的可实现性被高估,回退链对一大类窗口实际无效,且'真黑 vs 假黑'三信号合议有一个信号在 CopyFromScreen 路径不成立。实测/已知:PW_RENDERFULLCONTENT(=0x00000002,规范未给常量值)对很多 GPU 加速/DirectComposition 窗口(Chrome、Electron、UWP、现代游戏)返回黑帧或部分黑——§7.4 已承认。但回退链 PrintWindow→WGC→CopyFromScreen 的第三跳 CopyFromScreen 只能截'当前可见、未被遮挡的前台像素',对'后台静默'目标根本不可用(目标不在前台)。因此对于'后台静默 + DComp 窗口'(如后台 Chrome 标签的视觉),回退链前两跳可能黑帧、第三跳因后台不可用,实际只剩 WGC 一条;而 WGC 对单窗口捕获需要该窗口支持且 Win10 早期版本对 per-window WGC 限制较多。§7.4 信号③'PrintWindow 失败返 alpha=0 vs 真黑 alpha=255'在 CopyFromScreen 帧上不成立(CopyFromScreen 不产 alpha 语义)。

- **修法**：(1) 在 §7.4 给出 PW_RENDERFULLCONTENT 的实际常量(0x2)并标注'对 DComp/GPU 合成窗口已知高概率黑帧',把 WGC 提为 DComp 窗口的首选而非回退第二跳;(2) 明确'后台静默 + 前台不可见'时回退链不含 CopyFromScreen 跳(它需提到前台,违反 silent),该组合若 WGC 也失败→直接 FAILED(blank_unrecoverable_background),不偷偷夺焦;(3) 把信号③限定为'仅 PrintWindow 帧适用',CopyFromScreen 帧只用信号①(跨后端交叉验证)+②(直方图)。在 §11/§12 增一条已知能力边界:'DComp 窗口后台像素捕获在部分 Win10 版本不可靠,fail-closed 申报而非保证'。

### 次要（3 条）

**次要.1** 过度工程:对'主屏全屏单点截图'(函级 shot.screen / mcp_fullscreen 路径)强套了为代码后端设计的全套闸门与回执字段,大量字段恒为空/恒为默认,制造噪声并稀释'可靠申报'的信号。mcp_fullscreen 路径:无候选(candidate_count 恒=1)、无遮挡概念(occluded 恒 no)、无 structured 泄露面(injection_surface 恒 low)、无 capture_mode、无 element_path、无 bring_to_front、像素打码由 MCP 内建(redaction.structural_* 恒空)。但 §9 固定回执信封要求每次都带全部字段,§7 状态机要求每次走完 PREFLIGHT→...→EXIT_GATE 全链。对最高频的'给我截个屏'用例,这是把一个本应 1 跳的操作套进 8 状态机 + 20 字段信封。

- **修法**：定义 mcp_fullscreen 为'快路径 profile':回执信封按 modality/backend 投影,无关字段显式标 N/A 而非填默认值(消除'occluded:no'被误读为'已检查无遮挡'的假信号——其实是'不适用');状态机对 mcp_fullscreen 允许塌缩为 PREFLIGHT→CAPTURING→EXIT_GATE(无 VALIDITY/SECURITY 代码闸门,因为 MCP 内建打码已是安全闸门)。在 §1/§9 写明'信封字段集随 backend profile 投影',保留'无论成败都申报'铁律但去掉恒定字段的仪式负担。

**次要.2** 次要矛盾:§4 函级预设 shot.diff 与 §2.5 sink.processing=diff 的归属重叠,且 diff 需要'上一帧'的会话态没有在状态机/回执里定义存储位与失效条件。shot.diff 是预设指令,sink.processing=diff 是轴参数,二者关系未说明(shot.diff 是否=展开为某固定 5 轴组合?)。更实质:diff 与 §10 去重的 perceptual-hash 环、validity 的 stale_frame(differs_from_last)都依赖'上一帧/上一哈希'的会话级状态,但'上一帧'的定义(同 target?同 element?跨 backend 比较?句柄 epoch 失效后是否清空基线?)在三处各自隐含,没有统一的'比较基线'对象。epoch 失效后若不清基线,diff/stale 会拿新窗口的帧跟旧窗口比,产生假 stale/假 change。

- **修法**：定义统一的 baseline 对象:键=⟨稳定句柄 fingerprint, element_path, modality⟩,值=⟨last_frame_hash, last_structural_hash, timestamp⟩,显式规定 epoch_token 失效即清空对应 baseline(回执 stale 判定置 uncertain 而非 stale)。在 §4 写明 shot.diff = 预设展开为 {when:on_change 或 now, sink.processing:diff, 绑定该 target 的 baseline};§10 去重环与 §8 stale_frame 复用同一 baseline 对象。消除三处各自维护比较基线的隐患。

**次要.3** 次要缺角:ELICIT 代级'返回取参问卷让 AI 现场组装'缺少对'AI 组装出的 ad-hoc 指令本身需不需要再过一次契约校验/约束矩阵'的说明,存在绕过 §2.7 的理论缝。§4 代级说 AI 据答组装完整 5 轴 + 模态私有子参数;但没说这个现场组装的指令是否强制回流 §2.7 兼容约束矩阵和 §3.2 解析期非法组合检查。若 ELICIT 路径是'信任 AI 组装的参数直接执行',则 AI 可能(因模型错误或被 untrusted 内容诱导)组装出本应被 §2.7 拒绝的非法组合,而预设函级路径有约束矩阵兜底、代级却没有。

- **修法**：在 §4 代级明确一句铁律:'ELICIT 现场组装的 ad-hoc 指令与函级预设走完全相同的契约校验入口——必过 §2.7 约束矩阵 + §3.2 解析期非法组合检查,校验失败回 FAILED(illegal_composition) 并附违反的具体约束行,而非执行'。把'代级=现场组装但不豁免任何契约校验'写死,堵住预设有兜底、ad-hoc 无兜底的不对称。
